# MineCore technical audit, version 1 (2026-10-25)

Scope: the owner's audit brief (verify what MineCore really computes, compare
with the functions Datamine documents for Studio NPVS, find gaps, fix
correctness problems first). Datamine's internal algorithms are not public;
the comparison is against functions, not code. Every status below is backed
by a test in this repository that was run for this audit, or it is marked E.

Evidence run (Linux, 2026-10-25): `uv run pytest` 444 passed before the audit
work; the new known-answer suite `tests/python/test_audit_known_answers.py`
11 passed; gates (ruff, ruff format, mypy, cargo fmt) pass. CI runs the same
on Windows and Linux for every PR.

## A. Executive summary

- The engineering chain from drillhole files to a scheduled pit is real
  computation end to end, with no hard-coded results or inert menu items
  (a search for placeholder results and unimplemented actions found none).
- Block tonnage, contained and recovered metal, block value, discounting and
  the ultimate pit pass hand-computed known answers (tests A to F). The
  ultimate pit is an exact maximum-closure solution (equivalent to
  Lerchs-Grossmann), checked against exhaustive search.
- One correctness defect was found and fixed: the pushback ore target counted
  in-situ ore tonnes while the shell report and the schedule count plant feed
  (after mining recovery and dilution). With 95 % mining recovery and no
  dilution a "5 Mt" pushback held about 4.75 Mt of feed. Test
  `test_pushback_ore_target_counts_plant_feed` fails on the old code and
  passes now.
- The main gaps for engineering use are economic and scheduling depth:
  no capital costs, royalties, payability or taxes in the cash flow; the
  production schedule is a constrained greedy sequence, not an NPV
  optimisation; no stockpile capacity or grade-blending targets; no
  sensitivity or scenario tools; no geological-risk, haulage or
  material-allocation modules.

## C. Mathematical model (as implemented)

- Block: V = dx dy dz (times the volume fraction for partial blocks);
  T = V rho; contained metal = T g f, f = 0.01 for %, 1e-6 for g/t and ppm.
- Value (single element): metal = T MR g f / m_unit, recovered = metal R;
  revenue = recovered (P f_rev - selling); feed = T MR (1 + D);
  ore when revenue > feed C_proc; value = revenue - feed C_proc - T C_mine,
  otherwise -T C_mine. MR mining recovery, D dilution, f_rev revenue factor.
  C_mine grows by a per-bench increment below the model top.
- Ultimate pit: maximise the sum of values over closed sets of the precedence
  graph (block -> blocks in its slope cone above); solved as a minimum cut.
- Schedule cash: CF_t = margin of ore fed - mining cost of rock mined;
  PV = CF_t / (1 + r)^t, end of period, t in years.
- Stockpile: S_t = S_(t-1) + I_t - O_t per route, blended grade.

## F. Known limitations

See `docs/KNOWN_LIMITATIONS.md`. In short for planning: the schedule is a
greedy sequence, not an optimisation; the cash flow has no capital, royalty
or tax terms; pushbacks follow nested shells and are not NPV-optimised (since done, item 6 below);
stockpiles have no capacity; the ultimate pit uses values rounded to 0.01.
